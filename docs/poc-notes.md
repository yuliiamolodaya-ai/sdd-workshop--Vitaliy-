# Нотатки PoC: що я побачив у запущеному застосунку

## Проба 1: обов'язковий телефон
Що змінив:
За RULE-06 (зараз «можна не вказувати» → має бути обов’язковий) і таблицею ключових файлів з Дня 2:

| Файл | Навіщо змінювати |
| --- | --- |
| `ContactForm.tsx` | Прибрати `.optional()` у схемі телефону; порожній номер має давати помилку (AC-01, AC-11) |
| `validateContactData.ts` | Перевіряти телефон завжди, не лише `if (phoneNumber)` (AC-02) |
| `ContactForm.test.tsx` | Зараз дозволяє відправити без телефону — додати/оновити кейси під обов’язковість |
| `validateContactData.test.ts` | Порожній телефон має стати помилкою |
| `uk.json`, `en.json` | Немає окремого тексту «телефон обов’язковий» (Q-05); потрібен ключ помилки порожнього поля |
| `errors.ts` | Англійська серверна помилка для відсутнього телефону (RULE-14), якщо її ще немає |

Не чіпати зараз: RULE-07…09 (формат і маска), файл/PDF (RULE-16), лист (RULE-17…18).
Спільна форма в `GetNotesModal` теж зачепиться (Q-11) — окреме рішення замовника.

Що побачив у браузері:
Форма англійською: ім’я, email, повідомлення й згода заповнені, телефон порожній. Після спроби надіслати — червона рамка біля телефону і текст «This field is required». Запит не пішов.
Позначка обов’язкового: так — у лейблі «Phone number *» (зірочка, як у інших обов’язкових полів).

Що показали тести:
Червоні тести — не баг, а знахідка: вони фіксували стару поведінку (RULE-06: телефон можна не вказувати), яку замовник змінює.

| Тест | Чому червоний |
| --- | --- |
| `ContactForm.test.tsx` → `should call onSubmit callback when submit button is clicked` | Надсилав форму без телефону і очікував успіх. Після обов’язковості `onSubmit` не викликається. |
| `validateContactData.test.ts` → `should return no errors for valid input` | «Валідний» набір без `phoneNumber` і очікування `[]`. Сервер тепер повертає `PHONE_NUMBER_ERROR`. |

Після оновлення очікувань під нову вимогу ці тести знову зелені; окремо додано кейс на порожній телефон.

## Проба 2: мінімальна довжина повідомлення
Що змінив:
RULE-05: мінімум повідомлення **10 → 5**. Зміни в усіх трьох шарах, інакше API і форма роз’їдуться:

| Файл | Зміна |
| --- | --- |
| `app/constants/validation.ts` | `MESSAGE_MIN_LENGTH: 5` (сервер, `errors.ts` підтягує сам) |
| `ContactForm.tsx` | `.min(lengths.MESSAGE_MIN_LENGTH)` замість захардкодженого `10` |
| `i18n/messages/uk.json`, `en.json` | Текст помилки: «…5 символів» / «…5 characters» |
| `ContactForm.test.tsx`, `validateContactData.test.ts` | Коротший приклад для кейсу «занадто коротке» |
| `docs/contact-form-feature.md` | RULE-05: від 5 до 1000 |

Що побачив у браузері:
У полі повідомлення введено `dddd` (4 символи). Форма не відправляється: червона рамка і «The comment must contain at least 5 characters». Менше п’яти — блокує; п’ять і більше пройдуть по довжині (інші поля ще треба заповнити).

Що показали тести:
Червоні тести — знахідка: зафіксований старий мінімум **10** (RULE-05), який змінюємо на 5.

| Тест | Чому червоний |
| --- | --- |
| `ContactForm.test.tsx` → `should show errors when incorrect inputs` | У повідомленні було `Привіт` (6 символів) і очікувалась помилка довжини. При мінімумі 5 це вже валідна довжина — текст помилки не з’являється. |
| `validateContactData.test.ts` → `should return error if message is too short` | `message: 'Too short'` (9 символів) очікував `MESSAGE_ERROR`. При мінімумі 5 сервер приймає таке повідомлення — помилки немає. |

Після оновлення тестових даних (`1234` замість `Привіт` / `Too short`) — знову зелені.

## Чекліст передачі (git diff + PoC)

Правило: **Доведено** — лише з блоків «Що побачив у браузері» / «Що показали тести» вище. Без запису — **не зафіксовано**. Рядки **«Потрібен розробник»** можна лишати **відкритими** — це чесний стан до узгодження з AC і замовником.

**Приклади питань для відкритих рядків:** чи зміна узгоджена з AC з Дня 2? Яке значення мінімуму правильне за вимогами замовника? Чи входить `GetNotesModal` у scope (Q-11)? Чи окремий текст помилки телефону (Q-05)? Чи `package-lock` свідомо в PR?
